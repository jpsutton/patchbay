# Patchbay Remote

The phone app: it joins a Patchbay mesh as a phone and drives the chats and Code sessions of the computers in it. Design: [docs/design/mobile.md](../docs/design/mobile.md). Using it: [docs/mesh.md](../docs/mesh.md#from-your-phone).

- `src-tauri/`: the Tauri app. Its backend (`src/lib.rs`) answers the desktop's commands by asking the gateway, through `crates/patchbay-mesh`'s `RemoteClient`. `gen/android/` is the Android Studio project, generated by `tauri android init` and kept in the repository.
- `plugin/`: Android services the app needs (Keystore sealing, the keep-alive service).
- `fdroid/metadata/`: the app's listing in Patchbay's F-Droid repository.
- `docker/`: an Android build environment, for machines without the Android SDK.
- The UI lives with the desktop's, in `../src/remote/` and `../remote.html`.

## Trying the UI in a browser

```bash
pnpm dev:remote
```

Then open `http://localhost:1424/remote.html`, with your browser's device toolbar set to a phone. A fake backend stands in for the mesh. Add `?join=1` to start at the join screen.

## Building the APK

With Docker and no Android SDK:

```bash
scripts/android-build.sh
```

That builds an unsigned release APK for arm64 under `src-tauri/gen/android/app/build/outputs/apk/`. Pass `--debug` for a debug APK signed with the debug key, which installs straight away:

```bash
scripts/android-build.sh --debug
```

```bash
adb install -r remote/src-tauri/gen/android/app/build/outputs/apk/universal/debug/app-universal-debug.apk
```

With the Android SDK, NDK 27, Java 21 and the `aarch64-linux-android` Rust target installed, the same build runs directly:

```bash
pnpm build:remote
```

```bash
cd remote && ../node_modules/.bin/tauri android build --apk --target aarch64 --config '{"build":{"beforeBuildCommand":""}}'
```

The desktop build of the app (`cargo run` in `src-tauri/`, after `pnpm build:remote`) works too, for trying it against a real mesh from a computer.

## Trying it end to end in an emulator

`scripts/android-e2e.sh` does the whole thing from a clean machine and checks the result:

```bash
scripts/android-e2e.sh setup   # once: JDK 21, command-line tools, SDK, an AVD named patchbay-e2e, the Rust target
scripts/android-e2e.sh up      # build, start, join, check; --fresh starts over, --headless hides the window
scripts/android-e2e.sh down    # stop the node and the mock model (--emulator stops the emulator too)
```

`doctor` lists what is missing without changing anything, and `status` shows what runs. `up` builds the debug APK and `patchbayd` (the desktop app's core, headless, with its web UI) from the same checkout, so phone and computer are always the same version; `status` compares the two builds. It starts `scripts/mock-llm.py` as the model (no key), makes a mesh that listens on `127.0.0.1` only, with one chat and one Code session, boots the emulator, installs the APK, joins as `e2e-emulator` through `10.0.2.2`, approves that one phone, and confirms over the app's web view that Chats, Code and the computer's name show what the node holds. It exits nonzero if anything is missing. The desktop UI of the same node is at the address `status` prints. Steps also run alone: `build`, `emulator`, `node`, `install`, `join`, `verify`, `shot`, `logs`.

Versions come from `remote/docker/Dockerfile`, so this and the container build do not drift. The emulator image is API 36 Google APIs (`arm64-v8a` on Apple silicon, `x86_64` elsewhere). It uses its own AVD and data under `~/.cache/patchbay-android-e2e`, never an emulator you made yourself. The drivers need Node 22+; `mock-llm.py` runs under `pipenv`. It has been run on macOS (Apple silicon) only. It stands `patchbayd` in for the desktop window. The Code session uses the built-in Patchbay agent, so no other agent has to be installed; the script checks that the phone lists the session but does not run a turn in it, so the `!edit` permission below is still tried by hand.

By hand, a gateway with something to drive: `scripts/mock-llm.py` as the model, and a test node that serves phones on port 41890 (passphrase `correct horse battery`), with a Code session on the Patchbay agent and a chat, approving every phone that asks to join:

```bash
scripts/mock-llm.py
```

```bash
cd src-tauri && cargo test --lib manual_phone_gateway -- --ignored --nocapture
```

Build for the emulator with `ANDROID_TARGET=x86_64 scripts/android-build.sh --debug`, install it on an x86_64 Android image, and join `10.0.2.2` (the emulator's name for the host). In the Code session, `!edit` makes the mock model ask for an edit permission, which the phone answers.

## Release keys (one-time setup, by a person)

Releases sign the APK and publish it to the F-Droid repository on GitHub Pages (see `.github/workflows/release.yml`). Until these secrets exist, releases go out without the phone app.

1. **APK signing key.** It can never change: Android refuses an update signed by another key. Back it up with the GPG release key.

   ```bash
   keytool -genkeypair -keystore patchbay-apk.p12 -storetype PKCS12 -alias patchbay -keyalg RSA -keysize 4096 -validity 10000 -dname "CN=Patchbay Remote"
   ```

   ```bash
   base64 -w0 patchbay-apk.p12 | gh secret set PATCHBAY_APK_KEYSTORE -R jpsutton/patchbay
   ```

   ```bash
   gh secret set PATCHBAY_APK_KEYSTORE_PASS -R jpsutton/patchbay
   ```

2. **F-Droid repository key.** It signs the repository's index; phones check its fingerprint. The alias must be `patchbay-fdroid`.

   ```bash
   keytool -genkeypair -keystore patchbay-fdroid.p12 -storetype PKCS12 -alias patchbay-fdroid -keyalg RSA -keysize 4096 -validity 10000 -dname "CN=Patchbay F-Droid repository"
   ```

   ```bash
   base64 -w0 patchbay-fdroid.p12 | gh secret set PATCHBAY_FDROID_KEYSTORE -R jpsutton/patchbay
   ```

   ```bash
   gh secret set PATCHBAY_FDROID_KEYSTORE_PASS -R jpsutton/patchbay
   ```

3. **GitHub Pages.** After the first release with the phone app creates the `gh-pages` branch: Settings → Pages → Deploy from a branch → `gh-pages`, `/ (root)`. The repository is then at `https://jpsutton.github.io/patchbay/fdroid/repo`.
