# patchbayd on Windows: managed updates with winget

The Windows daemon is a zip with no updater of its own. This sets up `winget` to install and update it from a manifest Patchbay publishes on GitHub Pages. Nothing is submitted to Microsoft's winget-pkgs.

## Use it

Once, in an administrator terminal:

```powershell
winget settings --enable LocalManifestFiles
```

Then, in any terminal:

```powershell
irm https://raw.githubusercontent.com/jpsutton/patchbay/staging/scripts/windows/Install-Patchbayd.ps1 -OutFile Install-Patchbayd.ps1
.\Install-Patchbayd.ps1            # installs; run it again to update
```

`patchbayd` is then on your `PATH`. Updating needs patchbayd stopped (winget cannot replace a running exe): stop it, or add `-StopRunning`. Your chats, sessions and token are in the data folder, not the install folder, so they are untouched. If the desktop app runs on the same computer against the same data folder, update both together: the app and the daemon must be the same version.

## How it works

`packaging/winget/jpsutton.patchbayd.yaml` is a winget singleton manifest: the release zip as a `zip` installer with a nested `portable` exe. The zip wraps everything in `patchbayd-<version>-windows-x86_64/`, so the `RelativeFilePath` to `patchbayd.exe` contains the version and changes every release. `scripts/ci/winget_manifest.py` writes the manifest from a downloaded zip and reads the hash and the exe path from the zip itself:

```bash
gh release download v<version> -p 'patchbayd-<version>-windows-x86_64.zip'
scripts/ci/winget_manifest.py --version <version> --zip patchbayd-<version>-windows-x86_64.zip \
  --url https://github.com/jpsutton/patchbay/releases/download/v<version>/patchbayd-<version>-windows-x86_64.zip \
  > packaging/winget/jpsutton.patchbayd.yaml
```

## Publishing (design, not yet wired)

- **Where:** the `gh-pages` branch, `/winget/jpsutton.patchbayd.yaml`, served at `https://jpsutton.github.io/patchbay/winget/jpsutton.patchbayd.yaml`. `apt-repo.sh` and `fdroid-repo.sh` already publish `/apt` and `/fdroid` to that branch as one fresh force-pushed commit that keeps the other's files. A `winget-repo.sh` would follow the same fetch-the-branch, refuse-to-wipe-on-failed-fetch, copy-the-file, force-push pattern.
- **Keeping it current:** a step in `release.yml`, after the Windows zip is attached to the release, runs `winget_manifest.py` on that zip and publishes the result (and commits it to `packaging/winget/`). It waits for the release hold to lift; until then the manifest is regenerated by hand with the command above.
- **Later (not planned here):** a native winget source on Pages (pre-indexed `index.db` in a signed MSIX) would give `winget search` and plain `winget upgrade`; it is not officially supported by Microsoft.

## What is not verified

`winget` exists only on Windows, so manifest validation (`winget validate`), the install and upgrade runs, and the script have not been run. What was checked on macOS: the hash and exe path come from the real v0.23.1 zip, and `scripts/ci/test_winget_manifest.py` passes. To check on Windows: the manifest validates; the install puts `patchbayd` on `PATH` and `patchbayd --version` reports the release; the web UI loads (see the Links note below); an upgrade to a newer manifest replaces the binary and leaves the data folder alone.

Links note: winget exposes `patchbayd` through a link in its Links folder. The daemon looks for its web UI next to its own binary (`current_exe`), so if Windows reports the link's path rather than the real one, the UI is not found and `PATCHBAY_WEB_DIR` must point at the install's `web` folder. Whether that happens has not been tested.
